# Plan: no-lead-left-behind

## Purpose

Show how Taras runs one AI-agent deployment end to end, smallest version that solves slow answers, lost leads and an empty CRM. Why and for whom: `docs/BRIEF.md`.

## Phases

- **Core** (about 10 hours at most): tickets T1-T8 (with T5a, T5b, T7a), small but finished; then apply.
- **Polish**: after applying, items P1-P18 in order, as time allows. A P item becomes a ticket when its turn comes.

IDs are unique across the project: T for tickets, P for polish items, D for decisions. Test cases keep their own numbers ("case 1"), from `delivery/test-cases.md`.

## Tickets

Code lives in `app/`, tests in `tests/`, evals in `evals/`, knowledge files in `knowledge/`. A ticket that ends with "Then: critic" gets the stage 5 critic before the next ticket starts; this file is the only list of them. Every chat creates its lead in code on the first message; the agent's `save_lead` only fills fields, so no chat can be lost to a skipped tool call. Total estimate ~5:00.

## Polish (in order)

- **P1.** Tuning loop started by simulated manager feedback, with a change note; T8 already shows a real loop started by an eval.
- **P2.** Scope agreement (the change note from P1 is its example).
- **P3.** Go-live checklist: acceptance, 30-minute training, rollout in waves.
- **P4.** Delivery playbook: grows the README's week by week into which document when.
- **P5.** Weekly client status.
- **P6.** Pilot report against a baseline (simulated, labelled).
- **P7.** Risk register; remaining ADRs.
- **P8.** Local name detection in redaction (NER model or a small local LLM, next to the regex), measured on a test case with a name only in free text: closes the known redaction limit without sending data out. Also a lead name saved in Latin ("Olena") against Cyrillic in the transcript ("Олена"). Idea, not yet weighed: a doubtful phone match (11 or 13+ digits) becomes `[PHONE?]` and the summary tells the manager to check the recording; in chats (P9) the agent asks the buyer to confirm the number.
- **P9.** Redact Telegram chats before Claude: phones and emails the buyer types become placeholders, and code saves the real values to the lead. Measured on a case where the buyer types a phone. Promised in D6.
- **P10.** Real Bitrix24 instead of SQLite.
- **P11.** Price lookup tool instead of the price list in the prompt, for prices too many or too fresh for a prompt.
- **P12.** LLM judge for wording and tone, which code cannot check, as extra test cases.
- **P13.** "Notes for product" in the README.
- **P14.** Local open-source chat model as an eval experiment: run the same 10 cases, compare pass rate and cost with Haiku. Not a replacement unless it passes.
- **P15.** Room ranges: "2-3" or "both" is an answer, saved as a range on the lead (changes the CRM contract), with a test case; today `rooms` is one integer, so the agent asks again.
- **P16.** Chats in SQLite instead of memory, so a restart forgets nothing: the whole chat (a qualification is ~20 messages, ~3k tokens, no trimming needed); a chat idle for 24 hours is deleted, to keep no personal data longer than needed. Each turn also stores its latency, tokens and cost, which is the log for diagnosing chats. Langfuse waits for a real pilot with several reviewers, self-hosted, so chats stay with the client.
- **P17.** A handoff ends when the manager closes it in the CRM (new status `closed`): the buyer's next message starts a fresh chat on the same lead, and the agent asks how it can help. Not by a timer: the AI must never come back while a manager is still on it. Changes the CRM contract, so it gets an ADR and a test case; after P16.
- **P18.** Right handoffs, not only well-formed ones (T5b makes them well-formed). Evals: messages the price list or policies answer (studios, mortgage, instalments, "are you an AI?") must not call `hand_off`, next to the cases that must; each runs 10 times, and the report gives the wrong-handoff and missed-handoff rates, judged by code (D17). In a pilot the same rate comes from managers marking each handoff "needed" or "not needed" in the CRM, which feeds P1. Seen live: "Привіт, є студії?" handed off. Measured in T7a: price questions handed off as "unknown" in about 5% of first messages; one rule cut it to 0 of 30 (`evals/results.md`).

## Decisions

D1-D14 come from the grill (2026-10-30); D15-D19 were settled before it.

- **D1.** Telegram via long polling: the bot runs only for the GIF and evals, so no public URL.
- **D2.** Model: Haiku 5.5 with a flat, step-by-step prompt (0.10/0.50 USD per M tokens, ~0.04 USD per eval run); Sonnet 5.5 (2/10 USD, ~0.74 USD per run) only if Haiku fails cases after one prompt fix. Source: platform.claude.com/docs/en/about-claude/pricing, seen 2026-10-30.
- **D3.** Every file in English; the bot replies in the buyer's language.
- **D4.** Client A (all numbers simulated): 2 residential complexes in Kyiv, 6 managers, ~400 inbound conversations a month, ~40% of CRM leads miss budget or rooms, median first reply 2 hours. Price list ~12 rows (flat types per complex, price per m2; payment: 100%, 12-month instalments, partner-bank mortgage). Policies: booking, viewings, what the agent never promises (discounts, completion dates).
- **D5.** One lead per buyer: the agent asks for a phone number during qualification; the after-call webhook finds the lead by phone, else creates a new lead. Ringostat sends no CRM lead id (help.ringostat.com webhook docs, seen 2026-10-30).
- **D6.** Redaction covers the call transcript only: code, not Claude: regex for phones and emails, plus the names we already know (the buyer's from the lead found by phone, the manager's from the payload's `employee_fio`; Ringostat sends no caller name). Sending text to Claude to clean it would defeat the purpose. Telegram chats go to Claude as written; the spec says so. Names only in free text slip through: a known limit, written under the test cases; P8 closes it. Redacting chats with placeholders is P9.
- **D7.** The agent says it is an AI in its first message and whenever asked; it never passes itself off as a human.
- **D8.** Handoff triggers: buyer asks for a person or sends `/manager` (any time, no Claude call); ready to view or book; question outside the price list and policies; complaint. The handoff tool sets lead status `handoff` with a reason; the buyer is told a manager writes within 15 minutes from 9:00 to 19:00 Kyiv time, and by 12:00 at other times (code picks the message by the hour; no "tomorrow": after midnight it would be wrong); manager notification is simulated (a log line). After handoff the agent only repeats that a manager is on it.
- **D9.** The after-call webhook simulates Ringostat's "call processed by AI" event: the after-call event has phone and recording link but no transcript. One Claude call on the redacted transcript writes the summary and the qualification fields, which Ringostat's own free-text summary does not fill.
- **D10.** Phone number: Telegram's share-phone button (`request_contact`) sends it in one tap as a field, not text, so our code saves it without passing it through Claude. Code, not the agent, shows the button twice at most: with the first reply and with the handoff message; it disappears once shared. No refusal detection: the agent never insists, and a lead without a phone stays keyed by Telegram ID (critic, stage 3). Duplicate leads that remain are a risk in the spec; managers merge them in the real CRM.
- **D11.** No n8n: one webhook and one CRM fit in a few tested Python lines; one line in the README says why.
- **D12.** No speech-to-text of our own: Ringostat already transcribes calls, so ours would only duplicate a vendor feature.
- **D13.** The 10 test cases: (1) price question -> exact price; (2) partial qualification -> asks the rest, phone included -> right lead fields; (3) wants a viewing -> handoff "viewing"; (4) `/manager` -> handoff, no Claude call; (5) question outside price list and policies -> no invention, handoff "unknown"; (6) asks for a discount -> none promised; (7) "are you human?" -> says it is an AI; (8) writes in English -> answers in English; (9) call from a known phone -> summary and fields on that lead; (10) redaction -> no phone, email or payload name in the request to Claude. Unit tests cover the rest (unknown phone -> new lead; after handoff the agent only repeats that a manager is on it).
- **D14.** One Sonnet comparison run at the end of core (~0.74 USD): Haiku vs Sonnet pass rate and cost per conversation in the README.
- **D15.** Leads in a simulated CRM (SQLite), not Bitrix24: Python stdlib, no server; Bitrix24 is P10.
- **D16.** Price list in the system prompt, not a tool: about 12 rows fit, and the agent cannot skip a lookup and invent a price; the tool is P11.
- **D17.** Evals judged by code; no LLM judge in core (P12).
- **D18.** Each test case checks actions and data (tool calls, lead rows, exact prices), not wording: wording varies per run.
- **D19.** No live bot: a GIF.
- **D20.** "Agent" is the one word for the AI, client documents included: it is the target role's word, and one term beats two (Taras's call).
